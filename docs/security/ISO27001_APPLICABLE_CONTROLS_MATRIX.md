# Applicable ISO/IEC 27001:2022 Themes Matrix

This practical matrix maps the Munazzim Ubuntu laboratory prototype to relevant ISO/IEC 27001:2022 and Annex A information-security themes. It is guidance for TRL 6 security verification only. It does not claim certification, formal compliance, or conformity with ISO/IEC 27001.

| Security Area | ISO/IEC 27001 / Annex A Theme | Munazzim Evidence | Status | Gap | TRL 6 Relevance |
| --- | --- | --- | --- | --- | --- |
| Identity and access management | Organizational and technological access control; secure authentication | Auth Emulator Email/Password accounts establish verified server sessions; APIs derive identity from the session. A two-user task exercise confirmed cross-user read isolation and update rejection. | PASS | Token expiry/refresh and broader route coverage are NOT VERIFIED. | High: retain repeatable access-boundary evidence. |
| Firestore data protection | Access control; secure configuration | Prototype ownership Rules passed isolated emulator tests for anonymous denial, owner allow, and cross-user denial across tasks, appointments, and AI logs. | PASS | Live emulator integration remains separate from this isolated test. | High: retain the isolated test and schedule a controlled live integration run. |
| Input validation | Secure development; application security | Empty local API requests returned HTTP 400; task/appointment date/time validation is implemented. | PARTIAL | No request-size limits or comprehensive negative test suite demonstrated. | Medium: retain bounded rejection evidence. |
| AI output handling | Secure development; data validation | Provider output is parsed, schema-validated, sanitized, intent-gated, and deduplicated before proposal output. | PARTIAL | Model-derived intent, semantic correctness, and full adversarial prompt handling are NOT VERIFIED. | High: show invalid-output rejection and user-confirmed action flow. |
| Change confirmation | Data integrity; secure development | Proposed AI task/appointment actions require the user to select `Save AI Actions` before their persistence calls. | PASS | AI interaction logging is separate and can occur without schedule-action confirmation. | Medium: distinguish proposal actions from log data. |

| Supplier/external service security | Supplier relationships; secure service use | Qwen is a private-address endpoint; Ollama is local fallback; provider calls use timeouts and fallback. | PARTIAL | Qwen transport is HTTP; provider trust, access control, and service hardening are NOT VERIFIED. | Medium: record boundaries and failure behavior. |
| Logging and monitoring | Logging; monitoring activities | Backup, Firebase, Next.js, and Ngrok logs are present; AI flow logging retains provider metadata without raw prompts/model responses. | PARTIAL | Existing historical logs, retention, access control, and alerting are NOT VERIFIED. | High: protect prototype schedule content and retain bounded test evidence. |
